# TaskFlow – Data Model Conventions

## Storage Keys

| Key | Type | Description |
|-----|------|-------------|
| `taskflow_tasks` | JSON array | All task objects |
| `taskflow_settings` | JSON object | User preferences |

Never use any other localStorage keys for application data.

## Task Schema

```js
{
  id:          String,   // UUID v4, generated by generateUUID() in utils.js
  title:       String,   // Required, 1–200 chars, trimmed
  description: String,   // Optional, max 1000 chars, default ""
  priority:    String,   // "Low" | "Medium" | "High"  — default "Medium"
  category:    String,   // Optional, max 50 chars, default ""
  dueDate:     String,   // "YYYY-MM-DD" | null
  dueTime:     String,   // "HH:MM" 24-hour | null  (only valid if dueDate set)
  status:      String,   // "pending" | "completed" | "overdue"
  createdAt:   String,   // ISO 8601 — new Date().toISOString()
  updatedAt:   String,   // ISO 8601 — updated on every save
  completedAt: String,   // ISO 8601 | null
}
```

## Settings Schema

```js
{
  theme:                String,  // "dark" | "light" — default "dark"
  notificationsEnabled: Boolean, // default false until user grants permission
  defaultPriority:      String,  // "Low" | "Medium" | "High" — default "Medium"
}
```

## Derived Fields (never stored, always computed)

- `isOverdue`: computed at runtime — `status !== 'completed' && dueDate && new Date(dueDate + 'T' + (dueTime || '23:59')) < new Date()`
- `timeRemaining`: computed by `countdown.js` every second
- `displayStatus`: "overdue" overrides "pending" when `isOverdue` is true

## Status Lifecycle

```
CREATE → status: "pending"
  → user marks complete → status: "completed", completedAt = now
    → user reopens → status: "pending", completedAt = null
  → deadline passes → displayed as "overdue" (computed, not stored separately)
```

Status field in storage is only ever "pending" or "completed". Overdue is a derived display state, not a stored value. This avoids stale overdue flags after editing due dates.

## Data Integrity Rules

1. Always call `validateTask(data)` before saving — returns `{ valid, errors }`
2. On `getTasks()`, filter out any items that fail schema validation (corrupted data)
3. On `saveTasks()`, always `JSON.stringify` the full array — no partial updates
4. Generate `updatedAt` on every edit, including toggling complete
5. Never mutate the task object returned from storage directly — always spread: `{ ...task, ...changes }`

## UUID Generation

Use `crypto.randomUUID()` if available (modern browsers), fallback to custom implementation in `utils.js`:

```js
export const generateUUID = () => {
  if (typeof crypto !== 'undefined' && crypto.randomUUID) {
    return crypto.randomUUID();
  }
  // Fallback: RFC 4122 v4 compatible
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, c => {
    const r = Math.random() * 16 | 0;
    return (c === 'x' ? r : (r & 0x3 | 0x8)).toString(16);
  });
};
```

## Date & Time Handling

- Always store dates as plain strings (`"YYYY-MM-DD"`, `"HH:MM"`) — not Date objects
- Parse to Date objects only when computing (countdowns, comparisons)
- For deadline DateTime: `new Date(dueDate + 'T' + (dueTime || '23:59:59'))`
- Never store timezone-offset strings — treat all as local time
- Format for display via `formatDate()` and `formatTime()` in `utils.js`

## Migration Strategy

When loading tasks, run a migration check:

```js
const migrateTasks = (tasks) => tasks.map(t => ({
  description:  '',
  category:     '',
  dueTime:      null,
  completedAt:  null,
  ...t,  // existing fields overwrite defaults
  updatedAt: t.updatedAt || t.createdAt,
}));
```

This ensures old data without newer fields still works after future schema additions.
